## 2. WBS 分解思路
  本次 WBS 分解严格遵循成果导向原则，围绕 “项目管理成果” 和 “业务功能成果” 两大一级交付物进行三级分解，思路如下：
按交付物类型划分一级节点
一级节点分为 “项目管理成果” 和 “业务功能成果” 两类，既覆盖实验要求的所有交付文档，也对应系统核心业务模块，避免了纯过程性描述。
  按阶段 / 模块细化二级节点
“项目管理成果” 分为 “启动与规划成果”“计划与管控成果”“配置与总结成果”，完整对应实验中启动说明、WBS、进度计划、配置管理和总结报告等交付物。
“业务功能成果” 分为 “活动管理成果”“报名与审核成果”“签到与统计成果”，严格匹配项目目标中活动发布、报名、审核、签到、导出五大核心功能域。
  三级节点全部为可交付成果
所有三级条目均为具体的文档、定义或设计草案（如项目启动说明书、活动发布信息字段定义、签到统计结果导出模板等），不包含 “开会”“讨论” 等过程性动作，完全符合实验对 “成果导向分解” 的要求。
  边界清晰，不包含实验范围外内容
分解过程中排除了项目边界中 “不纳入范围” 的内容（如复杂支付、统一身份认证对接、移动端开发等），确保 WBS 完全在实验范围内，不出现范围蔓延。

## 3. 进度安排依据
本组的简化进度计划主要依据以下几点制定：
  任务依赖关系
进度安排严格按照任务间的前置关系排期：
需求与边界确认（A1）是所有后续任务的基础；
WBS 分解（A2）完成后才能进行关键活动排期（A3）；
配置管理分支建立（A4）与 WBS 同步进行；
所有任务完成后，才能合并并提交总结报告（A5）。
  实验任务量与复杂度
每个关键任务（需求确认、WBS 分解、进度排期、配置管理、总结报告）均分配 1 天工期，与实验周期和任务复杂度相匹配，避免工期过紧或过松。
  角色分工与责任对应
进度计划中的每项任务都明确了责任人，例如 WBS 和进度计划由计划负责人主导，配置管理由配置管理员负责，确保责任清晰、进度可控。

## 4. 配置管理与协作过程
本组采用了规范化的 Git 配置管理流程，具体过程如下：
  分支策略
建立了 main、dev 和 feature-* 三级分支结构：
main 分支：最终交付分支，只接收合并后的稳定版本；
dev 分支：开发主分支，用于汇总所有 feature 分支的成果；
feature-zhangtan、feature-hedequan、feature-libai：成员个人任务分支，用于并行开发各自负责的文档。
  命名与提交规范
文档命名统一采用 0X-功能说明.md 格式，如 01-project-charter.md、02-wbs.md；
提交信息使用 类型: 简要说明 格式，区分 init、feat、docs、fix、merge 等不同类型，便于追溯。
  合并与冲突处理
单个任务完成并确认无误后，由配置管理员审核并合并 feature 分支到 dev；
所有任务完成后，经全体成员确认无错误，再将 dev 分支合并到 main；
合并冲突由涉及文件的两位成员共同协商解决，解决后提交 fix 类型的提交，保留冲突解决痕迹。

## 5. 冲突解决过程记录
  本次实验中，本组在协作过程中遇到的主要冲突及解决方式如下：
文档合并冲突
场景：多位成员同时修改 docs/05-summary-report.md 时，因编辑内容重叠产生文本冲突。
解决：由两位修改者共同协商，整合双方的合理内容，在文件中保留冲突标记与解决痕迹，提交 fix: 解决总结报告合并冲突 的提交后，再继续合并流程。
  分支合并时机冲突
场景：某成员的 feature 分支尚未完成，配置管理员尝试合并到 dev 时提示内容不完整。
解决：暂停合并，待该成员完成所有任务并确认文档无误后，再执行合并，避免引入未完成内容。

## 6. 经验与问题
  本次实验收获的经验
成果导向的 WBS 分解能够有效避免项目范围蔓延，让每个任务都有明确的交付物，更便于估算、排期和验收。
规范化的配置管理流程（分支策略、提交规范、冲突处理）是团队协作的基础，能显著减少版本混乱和合并问题。
明确的角色分工和前置依赖关系，能让进度计划更合理，避免任务并行时出现互相等待的情况。
  遇到的问题与改进方向
问题：初期对 Git 分支合并流程不熟悉，出现过误合并未完成内容的情况。
改进：后续严格执行 “feature 分支完成后再合并到 dev” 的规则，合并前由配置管理员进行二次检查。
问题：多人同时编辑同一文档时容易产生冲突，解决过程耗时较长。
改进：后续可采用 “按章节分工编辑文档” 的方式，减少多人同时修改同一文件的情况。
